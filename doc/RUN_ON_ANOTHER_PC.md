# Run **and recreate** the Wallet app on another PC

Two things this file lets you do:

1. **Copy-and-run** — take the existing folder to a fresh machine and boot the same app in ~10 minutes.
2. **Rebuild from scratch** — hand this file to an LLM (or a developer) and get back an app with the same colors, fonts, icons, spacing, components, layout, page structure, data model, and API.

Sections 1–9 cover copy-and-run. Sections 10–20 are the recreation specification.

---

## 0. What "the same app" means

- **Name in-product:** Vault — Personal Finance
- **Type:** desktop web app (no mobile build)
- **Stack:** Vite + React 18 + Tailwind (frontend) · Node + Express (backend)
- **Data:** all persistent state in `backend/sampledata.json`, encrypted at rest with **AES-256-GCM**
- **Themes:** light + dark (persisted, hydrated pre-paint to avoid FOUC)
- **Currency:** ₹ (INR) default; ~90 currencies + ~180 countries supported
- **No paid APIs.** No cloud sync. No bank connections. No mobile app. Everything runs on the local box.

# Part 1 · Copy-and-run

## 1. Prerequisites

| Tool | Minimum | Check | Install |
|---|---|---|---|
| Node.js | 18.x (tested on 22 / 25) | `node -v` | [nodejs.org](https://nodejs.org) → LTS |
| npm | 9.x (bundles with Node) | `npm -v` | — |
| PowerShell 5.1 (Windows) | any | `$PSVersionTable.PSVersion` | pre-installed |
| Ports `4000` & `5173` free | | `Get-NetTCPConnection -State Listen \| Where-Object {$_.LocalPort -in 4000,5173}` (returns nothing) | stop the owner or set `$env:PORT` |

No git, no bank keys, no paid subscriptions.

## 2. Copy the folder

Move the whole `Wallet/` folder to the new machine. Put it somewhere short like `C:\dev\Wallet\`.

**Skip when copying** (regenerated by npm install):

```
Wallet\backend\node_modules\
Wallet\frontend\node_modules\
```

**Bring both, or bring neither** — the encrypted data + its key are useless apart:

| File | Holds | If missing on the new PC |
|---|---|---|
| `backend\sampledata.json` | Encrypted users, transactions, budgets, bills, goals, debts, notification overlay | A fresh empty file is auto-created on first boot |
| `backend\.data-key` | 32-byte AES-256-GCM key for the file above | A fresh key is auto-generated on first boot (existing encrypted file becomes unreadable — treated as empty) |

**OneDrive / Google Drive caveat** — right-click the copied `Wallet\` → **"Always keep on this device"** so npm doesn't hit EPERM on cloud-only files.

## 3. Install

```powershell
Set-Location .\backend;  npm install; Set-Location ..
Set-Location .\frontend; npm install; Set-Location ..
```

## 4. Start backend (terminal 1)

```powershell
Set-Location .\backend
npm run dev            # nodemon — restarts on save
```

Expected boot log:

```
  [auto-post] checked (N active) · generated K scheduled transaction(s).
  Wallet backend running on http://localhost:4000
  Data-at-rest: aes-256-gcm · key source: <path>\backend\.data-key
  Registered users: <n>
```

If you see `EADDRINUSE :::4000`, port is busy. Either stop the owner (`Stop-Process -Id <PID> -Force`) or use another port:

```powershell
$env:PORT = '4001'
npm run dev
# then edit frontend/vite.config.js proxy target to match
```

## 5. Start frontend (terminal 2)

```powershell
Set-Location .\frontend
npm run dev            # vite
# ➜  Local: http://localhost:5173/
```

Open the URL. You'll land on the marketing page.

## 6. First login

- **Copied `sampledata.json` + `.data-key`** → log in with any user you had.
- **Fresh (no data files)** → click **Sign up**. Name / email / password (min 6 chars). No demo account exists.

## 7. Verify recent features work

- [ ] Sidebar shows **Recurring & Bills** (not "Bills"). URL `/app/bills`.
- [ ] Add-bill modal has **Type**, **Category (label)**, **Category (for posting)**, **Vendor**, **Payment method**, **Note**, and two checkboxes: **Auto-post to ledger** + **Autopay is set up**.
- [ ] With **Auto-post to ledger** on and a **Category (for posting)** picked, save → card shows a brand-tone **Auto-post** chip; hover reveals ⚡ Run-now + ⏸ Pause.
- [ ] Any modal: sticky header + sticky footer + scrollable body (max 90vh), subtle fade+scale on open.
- [ ] Settings sidebar has **no Recurring tab**.
- [ ] Goals: **New goal** modal has a 10-swatch color picker; hover a card → Edit + Delete icons; **Highest priority** panel names the highest-priority goal (not the hardcoded "Emergency Fund · 85%").
- [ ] Contribute button opens a **themed modal** with quick-add chips + live preview (no `window.prompt`).
- [ ] Debts: with 3 divergent debts, the callout under the chart names the winner (e.g. "Avalanche saves approx. ₹37,271 …") and offers **Switch to {winner}** when viewing the loser.
- [ ] Notifications page renders auto-generated rows when triggers exist (overdue bill, over-budget, goal reached, etc.) — no seeding.
- [ ] Read/dismiss state survives a full backend restart.

## 8. Troubleshooting

| Symptom | Fix |
|---|---|
| `EPERM` / `EACCES` during `npm install` on OneDrive | Right-click folder → **Always keep on this device** → retry. |
| Backend crash `EADDRINUSE :::4000` | `Get-NetTCPConnection -State Listen -LocalPort 4000` → `Stop-Process -Id <PID> -Force`, or set `$env:PORT`. |
| `nodemon: command not found` | `npm install` inside `backend/`, or run `npm start` (plain `node`). |
| Every API returns 401 immediately | Stale `wallet_token` in localStorage. DevTools → Application → Local Storage → delete → refresh → log in. |
| `Registered users: 0` after copying `sampledata.json` | You forgot `.data-key`. Copy it or accept a fresh start. |
| PowerShell blocks scripts | `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned` |
| Vite complains about a newish `crypto.hash` API | Upgrade Node to 18+. |

```powershell

Set-Location ..\frontend; npm install
Set-Location ..\backend;  npm run dev        # terminal 1
Set-Location ..\frontend; npm run dev        # terminal 2
# then open http://localhost:5173
```

## 10. Design tokens (colors, spacing, radius, shadow, animation)

All colors live as **`R G B`** triplets in CSS variables under `:root` (light) and `html.dark` (dark). Tailwind's `rgb(var(--x) / <alpha-value>)` format lets us reuse them at any opacity.

  --line:           226 232 240;  /* borders */
  --line-strong:    203 213 225;
  --tint:             0   0   0;  /* additive tint (black in light) */

    radial-gradient(900px 500px at 90% 10%, rgba(168,85,247,0.08), transparent 60%),

**Sizes:** `sm→max-w-md`, `md→max-w-lg` (default), `lg→max-w-2xl`, `xl→max-w-4xl`.

- Body scroll lock while open (`document.body.style.overflow = 'hidden'`)
- Backdrop click closes; inner card `stopPropagation`
- Long content scrolls **inside the body** — top and bottom stay pinned

## 17. Data model (backend `sampledata.json` schema)

Everything below lives per-user under `db.userData[userId]`. Top-level shape: `{ users: [...], userData: { [userId]: {...} }, sessions: {...} }`. AES-256-GCM encryption of the whole file.

```js
User = {
  id, name, email, phone, avatar,
  passwordHash, passwordSalt,       // scrypt + per-user salt
  currency: 'INR', currencySymbol: '₹',
  memberSince, plan, healthScore, healthGrade,
  twoFactorEnabled: false,          // stub
  biometricEnabled: false,          // stub
}

Account = {
  id, name, type: 'bank'|'savings'|'credit'|'cash'|'wallet',
  openingBalance, currency, color, icon, note,
  // live-derived (not stored): balance, inflow, outflow, txnCount
}

Category = { id, name, icon, color, parentId }     // parent supports sub-categories

Transaction = {
  id, date, type: 'income'|'expense'|'transfer',
  vendor, categoryId, amount,        // amount is negative for expense
  accountId?, fromAccountId?, toAccountId?,   // transfer uses from+to
  paymentMethod, note, labels: [], billId?    // billId set for auto-post rows
}

Budget = {
  id, categoryId, limit, period: 'weekly'|'monthly'|'yearly'|'custom',
  alertAt: 80, startDate?, endDate?,
  // live-derived: spent
}

Bill = {                                       // covers Recurring rules too
  id, name, type: 'expense'|'income'|'transfer',
  amount, category: '<string label>', categoryId,
  accountId, fromAccountId?, toAccountId?,
  paymentMethod, vendor, note,
  frequency: 'one-time'|'weekly'|'monthly'|'yearly',
  dueDate, status: 'pending'|'paid',
  autopay: bool,          // cosmetic chip only
  autoPost: bool,         // on due date, backend posts a real transaction and advances dueDate
  active: bool,           // pause auto-post
  lastRun: iso?
}

Goal = {
  id, name, target, saved, deadline?,
  priority: 'high'|'medium'|'low',
  monthlyContribution, color, note
}

Debt = { id, name, creditor, balance, apr, minPayment, dueDate }

Notification (overlay only — actual rows are generated on demand) = {
  id: 'gen_<kind>_<sourceId>',   // deterministic; kind = bill_overdue | bill_soon | budget_alert | budget_over | goal_done | insight_inactive
  read?: bool,
  dismissed?: bool,
}
```

`generateNotificationsFor(userData)` runs on every read of `/api/notifications` and returns rows built from budgets/bills/goals/transactions. `userData.notifications` stores only the read/dismissed overlay so state survives restarts. Legacy hand-seeded rows (with a title/body of their own) still render — backward compatible.

## 18. Debt payoff simulator (algorithm)

```
simulate(debts, extraMonthly, strategy):
  state = clone(debts) with numeric balances
  timeline = []
  totalInterest = 0
  for month in 0..480:
    push snapshot { month, total, [debt.name]: balance } into timeline
    break if every debt balance ≤ 0
    accrue interest = balance * (apr/100/12)
    pay minimums first
    target = strategy === 'snowball'
             ? smallest positive balance
             : highest APR positive
    apply extraMonthly to target (capped at target.balance)
    cascade any leftover once to the next-best
    advance dueDate per frequency
    if one-time bill: mark active=false, break its loop

  months = timeline.length - 1
  payoffDate = start + months
  return { timeline, totalInterest, months, payoffDate }
```

**Callout** below the chart, always visible on both tabs:

- If `avalanche.months === snowball.months && interest matches within epsilon` → neutral message *"Both strategies produce the same result for your current debts — this usually means the highest-APR debt is also the smallest balance…"*.
- Otherwise → brand-tone `border-brand-500/30 bg-brand-500/10` box: *"{winner} saves approx. ₹X in interest and ends Y months sooner than {loser}."* When the current tab isn't the winner, append a **"Switch to {winner}"** shortcut link.

### 24.6 Notification lifecycle
1. Backend derives rows from live data every `GET /api/notifications`.
2. User marks a row read → `PATCH /api/notifications/gen_bill_overdue_bill_123 { read: true }` — server upserts into `userData.notifications` overlay.
3. User dismisses another → `DELETE /api/notifications/gen_budget_over_bud_456` — overlay records `{ dismissed: true }`.
4. Backend restart → generator runs again, overlay is applied, dismissed rows stay hidden even if the trigger still holds.
5. User resolves the underlying condition (marks bill paid) → next fetch omits that row naturally; the overlay entry becomes dead weight (harmless).

## 25. API / data behavior details

### 25.1 Auth response shapes

```json
POST /api/auth/signup  → 201 { "token": "wtok_<hex>", "user": { "id", "name", "email", ... } }
POST /api/auth/login   → 200 { "token": "wtok_<hex>", "user": { ... } }
POST /api/auth/logout  → 200 (or 204)
```

Frontend stores the token in `localStorage.wallet_token`. Every subsequent request sends `Authorization: Bearer <token>`. On any 401 (except `/auth/*`) the client clears localStorage and force-redirects to `/login`.

### 25.2 Error envelopes

Non-2xx responses return JSON:

```json
{ "error": "<machine_code>", "message": "<human-readable>" }
```

Examples: `{ "error": "invalid_input", "message": "Email and a 6+ character password are required." }`; `{ "error": "not_found" }`; `{ "error": "not_auto_post", "message": "Only auto-post bills can be run." }`.

### 25.3 Live-computed vs. stored fields

Never store these — always derive on read:
- `account.balance`, `account.inflow`, `account.outflow`, `account.txnCount` — from all transactions touching that account.
- `budget.spent` — sum of transactions in the budget's category (and sub-categories) within its period window.
- `dashboard.spendingTrend`, `dashboard.categorySpend`, `dashboard.metrics` — from transactions.
- `notifications` — from budgets/bills/goals/transactions.

Stored (persisted):
- Anything the user typed: name, amount, categoryId, dueDate, priority, color, etc.
- Overlay state: `userData.notifications[]` (`{ id, read?, dismissed? }`).
- Bill fields advance on auto-post: `dueDate` and `lastRun` are mutated in place.

### 25.4 Cache / ETag rules

- Every safe GET goes through `sendCached(req, res, key, buildFn)` which returns `304 Not Modified` when the client's `If-None-Match` matches.
- Cache key = `<etagBase>:<userId>:<route>` — never leaks across users.
- Any mutating handler calls `bumpCache()` which rotates `etagBase` (invalidates every entry globally).
- Headers on every cached response: `ETag: W/"<hash>"`, `Cache-Control: private, no-cache` (browsers still hit the server, but only to revalidate).

### 25.5 Auto-post generator

Runs during `loadSync()` at boot **and** on any `POST /api/bills/:id/run`. For each bill where `autoPost && active !== false && dueDate`:

- Iterate up to 24 months forward as long as `dueDate ≤ today`.
- Post a transaction: `{ id: 'txn_...', date: dueDate, vendor: bill.vendor || bill.name, categoryId, amount: (type==='expense' ? -1 : 1) * bill.amount, type, paymentMethod, note: (bill.note ? bill.note + ' · ' : '') + '[recurring]', labels: ['recurring'], billId }`. For transfers: `fromAccountId` / `toAccountId`; otherwise `accountId`.
- Advance `dueDate` per frequency (`daily/weekly/monthly/yearly`; one-time flips `active=false` and `status='paid'` then breaks).
- After the loop, set `bill.lastRun` to now-ISO.

Boot log line: `[auto-post] checked (N active, K paused) · generated M scheduled transaction(s).`

### 25.6 Migration from legacy `recurringRules`

If `userData.recurringRules[]` is non-empty at boot, each rule is folded into `userData.bills[]` with `autoPost: true`, then the array is drained. Boot log: `[migrate] folded N recurring rule(s) into bills (one-time).` Idempotent — runs cleanly if there's nothing to move.

### 25.7 Notification generation contract

Every `GET /api/notifications`:
1. Run `generateNotificationsFor(userData)` → list of rows with deterministic IDs.
2. Overlay `userData.notifications[]` for `{ read, dismissed }` per ID.
3. Filter out dismissed. Assign `read` from overlay (default false).
4. Append any legacy hand-seeded rows (id NOT starting with `gen_`) that still have a title.
5. Sort by tone (danger < warning < success < info < neutral), then by id.

`PATCH /api/notifications/:id` and `DELETE /api/notifications/:id` **always succeed** — they upsert overlay records even if the ID doesn't correspond to a currently-generated row. This means "dismiss ahead of time" also works.

`POST /api/notifications/read-all` upserts `read: true` for every ID currently returned by the generator.

### 25.8 Contribute cap

`POST /api/goals/:id/contribute { amount }` sets `goal.saved = min(goal.target, goal.saved + amount)`. Client-side preview also caps at target so the button shows `Add ₹<capped>`, not the raw input. Extra pointed out to the user via amber note before submit.

### 25.9 Currency & FX

- User's currency stored on the user record (`user.currency`, `user.currencySymbol`).
- `formatCurrency(n)` reads user prefs → `formatCurrency(-649)` → `-₹649`. Locale-aware `toLocaleString`.
- Live FX rates fetched from Fawaz Ahmed's Currency API (`https://cdn.jsdelivr.net/gh/fawazahmed0/currency-api@1/latest/currencies/<base>.json`). No API key needed.
- Multi-currency accounts allowed; per-account conversion is on the roadmap but not implemented — currently all totals assume the user's main currency.

### 25.10 Session / expiry

Sessions live in `db.sessions[token] = { userId, createdAt }`. `SESSION_MAX_AGE_MS = 30 * 24 * 60 * 60 * 1000` (30 days). Expired tokens return `{ error: 'expired' }` with 401. Frontend force-logout on any 401.

## 27. Feature-level functionality details (edge cases & guarantees)

### 27.1 Auth
- Password minimum 6 characters (enforced client + server).
- Email normalized to lowercase before match on login.
- scrypt with a per-user random 16-byte salt; timing-safe comparison.
- Signup returns 400 `email_taken` if the email already exists (case-insensitive).
- Token invalidation: `POST /api/auth/logout` deletes the session server-side; client-only logout also just clears localStorage.

### 27.2 Transactions
- Type migration on PATCH: if the payload type changes (e.g. expense → transfer), the server rebuilds the transaction with the correct account fields (`accountId` → `fromAccountId` + `toAccountId`, and vice versa).
- Bulk import (`POST /api/transactions/bulk { rows: [...] }`) tolerates partial failures — returns `{ created: N, errors: [...] }`.
- Amount sign convention: expense stored **negative**; income and transfer stored **positive**. Frontend never negates on display — it renders `-₹X` from the sign.
- Sub-categories: when a transaction hits a parent category, budgets/reports/analytics also count sub-category spend under the parent.

### 27.3 Budgets
- `spent` recomputed on every read (never cached). Includes transactions from the budget's category AND any category whose `parentId` matches it.
- Custom period: transactions between `startDate` and `endDate` inclusive.
- Alert threshold `alertAt` defaults to 80. Rose progress bar at ≥ 90%; amber at ≥ 75%; brand otherwise.

### 27.4 Recurring & Bills
- One-time auto-post bills fire once, mark themselves `active=false` and `status='paid'`, then never fire again.
- Paused bills (`active: false`) skip auto-post on boot but **can still be manually run** via `POST /api/bills/:id/run` — Run now is a manual override.
- Deleting a bill does **not** roll back generated transactions (they stay in the ledger with the now-orphaned `billId`).
- Bills with a past `dueDate` at boot get caught up (up to 24 months of history) so long weekends don't break the ledger.
- `POST /api/bills/:id/run` refuses non-auto-post bills with `400 not_auto_post`.

### 27.5 Goals
- Contribute caps at target — you cannot save over-target. Extra is silently discarded (with UI warning).
- Highest-priority hero sort: (high > medium > low) then (higher completion %). Ties broken by array order.
- Deleting a goal removes it — no soft-delete.

### 27.6 Debts
- Simulator caps at 480 months (40 years). If real payoff needs more, the app returns 480 (rendered as `40+ years`) — extreme edge case only.
- Interest accrues monthly = `balance * (apr / 100 / 12)`.
- Extra payment applies to the strategy target, cascading remainder to the next-in-line once (max two debts touched per month with the extra).

### 27.7 Notifications
- Deterministic IDs: `gen_bill_overdue_<billId>`, `gen_bill_soon_<billId>`, `gen_budget_over_<budgetId>`, `gen_budget_alert_<budgetId>`, `gen_goal_done_<goalId>`, `gen_insight_inactive`.
- Overlay entries with no matching current generation are kept forever (small cost, big compatibility win).
- Frontend tone override: server-provided `tone` beats the type's default tone (so a `type: 'bill'` overdue is red, due-soon is amber, both share the same chip label `Bill`).

### 27.8 Modal
- `Escape` closes.
- Body scroll lock via `document.body.style.overflow = 'hidden'` (restored on unmount).
- Backdrop click closes; card `stopPropagation` prevents inner clicks from bubbling.
- Focus is NOT trapped currently — pressing Tab past the last focusable element escapes to the backdrop / page. TODO if you need strict a11y compliance.
- No focus-restore to the trigger element on close (browser default).

### 27.9 PIN lock
- 4–8 digit PIN, hashed with Web Crypto `subtle.digest('SHA-256', ...)` + a random salt (16 bytes) stored in `localStorage.wallet_pin_meta`.
- After idle-lock (or full page reload if a PIN is set), the `PinLockScreen` replaces the whole app until the correct PIN is entered.
- Wrong PIN attempts NOT rate-limited — brute force resistance is left to OS-level protections.

### 27.10 Idle logout
- Watches `mousemove`, `keydown`, `click`, `scroll`, `touchstart`. Timer resets on any of those.
- Idle threshold configurable via Preferences (`Never`, `5 min`, `15 min`, `30 min`, `1 hour`; default 30 min).
- 60 seconds before logout, a countdown modal appears: title `Are you still here?` — action `Stay signed in` (dismiss) or `Sign out now`. If the user does nothing, `logout()` runs (clears localStorage, redirects to `/login`).

## 28. TL;DR — four usage modes

- **Copy-and-run** on a fresh PC → follow §1–§9.
- **Recreate the visual system** from scratch → paste §10–§16 into an LLM.
- **Recreate exact copy and flows** → also include §23–§24.
- **Rebuild data + API guarantees** → include §17–§19 and §25–§27.

Pasting **§10 through §27 in full** gives an LLM everything it needs to produce an implementation that's visually, functionally, and behaviorally indistinguishable from the running app — same colors, same fonts, same icons, same UI components, same spacing, same page structure, same copy, same validation, same API, same flows, same edge cases.

The only thing this document can't guarantee is the *running behavior on your specific hardware* — for that, use Part 1 to actually run it and Part 2/3 as the spec you're checking against.
